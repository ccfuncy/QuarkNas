# 参考项目功能提炼与借鉴清单

> 用途：后续开发的功能取舍依据。对比对象为 `QuarkPan-plus`（开源 Python 客户端/CLI）与 `fnOS-quark`（闭源 fnOS FPK）。
> 范围约束（既有决策）：仅备份本人账号文件到 NAS；手动选文件；不做订阅式自动同步、不做分享链接转存、不做改名/刮削/媒体库刷新；交付形态为 Docker Compose。

---

## 一、QuarkPan-plus（youpingfang，MIT）

**定位**：夸克网盘的 Python SDK + 命令行工具，发布到 PyPI（`quarkpan-plus`）。面向脚本自动化与 Obsidian 笔记库同步等场景，不是 NAS 应用。

### 功能清单

| 模块 | 能力 |
| --- | --- |
| 认证 | 官方 API 二维码登录（生成 `config/qr_code.png` + 终端 ASCII 二维码）；手动 Cookie 登录作为兜底；登录态检查 / 刷新 / 登出；Cookie 存 `config/cookies.json`（可选加密）；多账户管理（规划中） |
| 文件管理 | 文件夹浏览（分页、递归、路径导航）；全盘搜索（文件名与内容匹配、按类型过滤）；创建 / 删除 / 重命名 / 移动；批量选择；容量用量查询 |
| 上传 | 单文件、整文件夹上传，大文件自动分片 |
| 下载 | 获取直链；按 fid 下载到本地；进度与速度显示；大文件断点续传 |
| 分享 | 创建分享（密码、有效期）；分享列表管理；分享转存到指定目录；分享链接智能解析；批量转存；批量分享（深度、分享层级 files/folders/both、排除目录、dry-run、CSV 输出） |
| CLI | 交互式文件管理器（方向键 + `ls` 后按序号执行 `cd 3` / `download 2` / `rm 2 3 4`，`#3` 消歧）；Rich 彩色输出；覆盖全部功能的命令集；示例脚本 |

### 工程结构

`quark_client/` 下分为 `core/api_client.py`（HTTP 与 API 封装）、`services/`（file / upload / download / share / name_resolver）、`auth/`（login / api_login / simple_login）、`cli/`（main / interactive / commands）、`utils/`。配置与登录态集中在 `config/`。

### 可借鉴点

1. **服务分层**：把「文件 / 上传 / 下载 / 分享」拆成独立 service，而不是一个大的 API 客户端。我们目前 `app/quark/client.py` 是单文件，功能继续增长时可按同样的切分方式拆分。
2. **直链获取 + 本地下载**的两段式封装，与我们 `engine.py` 的设计一致，可作为交叉验证的参考实现。
3. **登录态 refresh**：与我们本次补的 `refresh_session()`（补 `__puus`）思路一致——说明「扫码拿到的 Cookie 不完整、需要二次刷新」是通病，不是我们独有的坑。
4. **搜索接口**：全盘搜索 + 类型过滤，我们目前只有前端本地过滤（仅过滤当前页），可考虑接服务端搜索。
5. **容量信息**：`get_storage_info()` 可直接支撑账号卡片（总容量 / 已用）。

### 不借鉴

分享、转存、批量分享、上传、CLI 交互模式——均超出「自己账号 → NAS 备份」的范围。

## 二、fnOS-quark（ElyDemiurge，闭源）

**定位**：飞牛 fnOS 的原生应用（FPK 安装包），最低 fnOS `1.1.8`。仓库只发布 README、截图与 LICENSE，**无源码**；明确「为防止滥用，暂不提供 docker 版本」。因此只能参考产品设计与参数取值，不能复用代码。

### 功能清单

**浏览与下载**
- 网盘浏览与排序（名称 / 大小 / 更新时间），桌面与手机端均支持
- 文件、文件夹下载，可选保留网盘目录结构
- 扫码登录（夸克 App）或 Cookie 登录；账号页显示昵称、会员身份、到期日期、网盘空间
- 暂停、恢复、重试、优先下载、断点续传
- 多目录增量同步：默认每 60 分钟检查，首次全量、之后只下新增，不校对旧文件；云端删除不影响本地

**下载设置（默认值，可作为我们参数基准）**

| 设置 | 默认 / 取值 |
| --- | --- |
| 下载目录 / 默认目录 | 需先在系统授权；未勾选「默认」则每次询问 |
| 保留网盘目录结构 | 关闭 |
| 同名文件处理 | 默认「保留原文件并停止」；可选覆盖、保留二者、跳过 |
| 下载并发数（文件数） | 1–5，默认 3 |
| 单文件连接数 | 3 / 6 / 9 / 12，默认 6 |
| 硬盘预留空间 | 10 GB |
| 总下载限速 | 0（不限速），全任务共享 |
| 指定下载时段 | 默认关闭，支持跨午夜 |
| 网络错误自动重试 | 3 次，间隔 120 秒 |
| 浏览器通知 | 默认关闭，需页面打开并授权 |

**任务规则**
- 关闭网页后下载继续；未完成任务排在历史之前
- 文件夹任务可展开看子文件进度与失败原因；排队子文件可优先或取消；已开始传输可暂停
- 取消单文件删临时文件；取消文件夹可选保留或删除已完成文件；删除记录不删文件
- 退出或 Cookie 失效自动暂停任务，重新登录原账号后恢复进度

**观测与运维**
- 速度曲线：最近 10 分钟总速度 + 单文件曲线，重启清空
- 预计剩余时间（ETA）
- 日志搜索 / 分类 / 级别筛选；诊断包导出（脱敏，不含 Cookie / token / 文件内容）
- 崩溃报告与自动重启
- 应用内更新：多线路（自动 / GitHub 直连 / GH-Proxy / 自定义 HTTPS 代理），校验大小与 SHA-256，下载中断可继续
- 访问令牌（首次输入 token 才能进入，类似我们的 `AUTH_PASSWORD`）
- 移动端适配；刷新后保持当前页面
- 数据目录约定：`config / data / downloads / logs`，卸载不删数据

### 可借鉴点（按优先级）

- **P0**：暂停 / 恢复（我们只有取消 + 重试）；单文件连接数与并发数做成可配置项（现在写死在环境变量，无 UI）；同名文件策略目前只有「跳过」，可补「覆盖 / 保留二者」，但默认仍保持「跳过」。
- **P1**：速度曲线与 ETA；日志页与脱敏诊断导出；移动端适配；刷新后保持当前目录；任务分组（文件夹任务可展开）。
- **P2**：总限速、下载时段、浏览器通知；应用内更新在容器场景改为提示拉取新镜像。

### 与我们的关键印证

其 FAQ 要求 Cookie 登录时「从发往 `drive.quark.cn` 的请求标头复制完整 Cookie」，与我们本次定位的 **412 根因（缺少 `__puus`）** 完全吻合：直链 CDN 在签名校验之后还要用 `__puus` 做会话二次鉴权，扫码流程拿到的 Cookie 默认不含该字段，需主动从 `/1/clouddrive/member` 补抓。

## 六、下载速度封顶研究与「不用 Cookie」路线评估（2026-10-31）

### 6.1 现象

- 用户观察：夸克**官方客户端**可跑到 40+ MB/s；走**网页/Cookie 直链**最多约 2 MB/s（百度网页版同样约 2 MB/s）。
- 我们账号：`member_type = EXP_SVIP`（体验 SVIP，到期 2027-02-07），`is_new_user = true`，`member_status` 中 VIP / SUPER_VIP / Z_VIP / MINI_VIP 全为 `UNPAID`，`acc_status = 0`。

### 6.2 实测数据（同一 45.4 MB MP4，host `dl-pc-sz.drive.quark.cn`，`__puus` 已补齐）

| 场景 | 聚合吞吐 |
| --- | --- |
| 单连接顺序下载 32 MB | 2.88 MB/s |
| 32 连接 × 1 MB | 2.81 MB/s |
| 4 连接 × 8 MB（同一条直链） | 5.24 MB/s |
| 4 连接 × 8 MB（4 条不同直链） | 5.26 MB/s |
| 4 连接 × 8 MB（同一条直链，复测） | 5.22 MB/s |
| 8 连接（早前 24 MB 窗口） | 5.63 MB/s |

**结论**：
1. 单请求约 2.8 MB/s，聚合稳定封顶 **5.2–5.6 MB/s**（≈45 Mbps），三轮复测偏差 <1%。
2. **不是按直链限速**：4 条不同直链与同一条直链的总吞吐完全一致。
3. **不是按连接数线性放开**：32 连接反而回落到 2.8 MB/s（每连接分片太小，握手开销占比高），说明是账号/通道级令牌桶，不是「每连接一份配额、可叠加」。
4. 此前「本地宽带 ≈45 Mbps」的判断是错的——客户端能跑 40+ MB/s，说明本地带宽充裕，封顶在网盘侧。

### 6.3 为什么官方客户端快

- **百度**：官方会员充值页明确写「使用客户端下载文件时，**专享下载高速通道**」——网页通道被有意降级，是产品策略，不是技术限制。
- **夸克**：官方帮助中心把「并行任务数 / 下载限速」放在客户端；官方口径为免费档 2–4 MB/s、SVIP 30–50 MB/s（均为客户端数据）。
- **账号权益**：本账号是「新用户体验 SVIP」，付费档位全部 `UNPAID`、`acc_status = 0`，很可能只享有体验档的下载通道。
- **接口线索**：`/1/clouddrive/file/download` 返回 `metadata = {"dms": true, "acc1": "90", "acc2": "95"}`（base64 后为 90/95），疑为加速权重/配额，含义未公开；`range_size = 10485760`（10 MB）暗示服务端预期的分片粒度。
- **动态加速**：社区实测存在「加速试用 30 秒」按钮，试用期内可到 35 MB/s，说明限速是服务端动态策略，而非固定套餐值。

**结论：差距来自「客户端身份 + 通道分级」，不是我们实现有 bug。继续加并发无法突破 5.2 MB/s。**

### 6.4 非 Cookie 路线评估

| 方案 | 可行性 | 速度预期 | 成本 / 风险 |
| --- | --- | --- | --- |
| **A. 官方客户端下载 + 目录归档**（常开 Windows/macOS/Android 设备下载到共享目录，fnOS 挂载） | 可行 | 40+ MB/s（客户端原速） | 需一台常开设备；QuarkNas 只做「选文件 → 清单 → 校验 → 归档」，不承载字节流 |
| **B. 模拟客户端协议**（device_id / qimei / 私有签名 / 客户端版本 4.10.0） | 技术上可能 | 未知，需大量逆向 | 高维护成本、随客户端升级失效、有封号与 ToS 风险，**不建议** |
| **C. P2P / 快传** | 官方功能 | 3–8 MB/s | 需第二台设备配合，且慢于现状 |
| **D. 官方开放接口 / 官方 CLI** | 夸克**确实有**：`open-api-drive.quark.cn`（OAuth 2.0 + 签名）+ 官方 Node CLI；百度无官方 CLI，第三方 bypy/BaiduPCS-Py 仍走网页通道 | **实测 0.37 MB/s**（45.45 MB / 124.2 s），比 Cookie 直链还慢 14 倍，见 6.7 | 合规但无速度收益；CDN 为 `dl-sz.open-drive.quark.cn`，直链脱离 CLI 单独取用会 412 |
| **E. 第三方挂载**（alist / CloudDrive2） | 可行 | 与我们同级（同样走 Cookie 直链） | 无速度收益 |
| **F. 接受 5 MB/s** | 现状 | 5.2–5.6 MB/s ≈ 18–20 GB/h | 夜间备份 100 GB 约 5–6 小时，满足个人备份 |

### 6.5 建议

1. **短期（保持现状）**：Cookie 直连。快节点连接数维持 4–6 即可（实测再多无收益，还增加风控面）；慢源站由自动扩容升到 16 段，无需手工调整。把大批量任务放到夜间/非高峰，免费档高峰会从 3–4 掉到 1–2 MB/s。
2. ~~**中期（要 40 MB/s 只能走旁路）**：方案 A——在常开 Windows 主机或虚拟机里跑官方客户端~~ → **已否决（2026-10-31 决策）**。理由：需要额外常开 Windows 主机；官方桌面客户端无命令行接口、本机也未注册 `quark://` 之类的协议唤起，下载仍需人工在客户端点选，自动化程度低，收益仅是把 5.2 MB/s 提到客户端速度，不值当。**下载通道维持 Cookie 直链。**
3. **不做**：方案 A（客户端旁路）、方案 B（客户端协议逆向）、方案 C（P2P）、方案 E（第三方挂载）。

### 6.6 待验证

- 付费 SVIP 的 Cookie 直链是否仍封顶 5 MB/s（决定「升级会员」这条选项是否有效）。
- 官方开放接口（6.7）的下载速度是否与客户端同级。

### 6.7 官方 CLI 实测记录（2026-10-31）

**来源**：夸克官方「网盘 Skill」包 `https://pdds.quark.cn/download/stfile/uu66xuuuuuvyuw8wx/quarkclouddrive-1.0.20.zip`（237 KB），内含 `SKILL.md`、`scripts/quark-drive.cjs`（601 KB，Node，要求 Node ≥ 16）、`scripts/install.sh`、10 份 `references/*.md`。

**技术路径（非 Cookie）**：
- 域名：`open-api-drive.quark.cn`（API）、`pan.quark.cn`（OAuth 授权页）
- 授权：`/open/v1/oauth/authorize` → 回调拿 code → `GET /open/v1/oauth/token`（`grant_type=authorization_code`、`client_id`、`client_secret`、`scope=clouddrive.base\`clouddrive.netdisk`）
- 调用：`buildUrl` 附加 `req_id / access_token / device_id / platform`，另加签名头与 `x-pan-client-token`、`X-Agent-ID`、`Authorization: Bearer`；响应头 `x-new-access-token` 可续期
- 下载：`POST /open/v1/file/get_download_url {fid}`（批量 `/open/v1/file/multi_get_download_url`），内置 Checkpoint 断点续传，进度以 NDJSON 输出

**问题与绕过**：
- 裸跑报 `{"code":-104,"msg":"无法识别当前 Agent 环境，禁止继续使用"}`。经反混淆确认这是**本地**硬编码白名单（`he()` 遍历 22 个 Agent 探测函数，命中才放行），不是服务端风控；报错文案在源码中以 unicode 转义存储，故全文检索中文搜不到。
- 设 `CLAUDECODE=1` 后可越过该检查，转为 `{"code":-103,"msg":"未登录，请先执行 login 命令完成登录授权"}` → 说明命令行路径本身可行，只差 OAuth 授权。

**命令集**：`login [--token <授权码>] / unauthorize / logout / browse / search / download --fid <fid> --output-dir <dir> [--overwrite] / download list|resume|delete / upload / share / get-user-info / rename / move / organize / summary / qa / update`。

**对项目的意义**：
1. ~~这是目前唯一「合规 + 可能拿到客户端级速度」的路线~~ → 已实测否定，速度仅 0.37 MB/s，不适合作为下载通道。
2. 仍有价值的地方：`browse / search` 可用于「选文件」这一步的稳定元数据来源；OAuth token 比 Cookie 更稳（不怕 `__puus` 失效）。
3. 落地约束：容器内需 Node 运行时（镜像体积 +~50 MB）；`login` 需扫码（可用 `login --token` 传授权码，适配无头环境）；token 需持久化并做续期。

**实测结果（2026-10-31，同一 45.45 MB MP4）**：

| 通道 | 吞吐 | 备注 |
| --- | --- | --- |
| Cookie 直链（4–8 连接） | 5.2–5.6 MB/s | 本项目现状 |
| **官方 CLI（开放接口）** | **0.29–0.37 MB/s** | 三次独立测量：45.45 MB / 124.2 s = 0.37；5.82 MB / 20.4 s = 0.29；5 秒一次采样连续 70 s 稳定在 0.27–0.36 |
| 官方桌面客户端 | 40+ MB/s（用户实测） | 唯一真正的高速通道 |

- CLI 下载走 `dl-sz.open-drive.quark.cn`（独立 CDN），与网页直链的 `dl-pc-sz.drive.quark.cn` 不是同一套。
- 下载期间实测有 **4 条并发 TCP 连接**（同一 CDN 边缘 IP），聚合仍只有 ~0.3 MB/s → 不是单连接问题，是**账号/通道级限速**，约 **2.4–3 Mbps**。
- 把该直链提取出来单独请求一律返回 **412**（带 UA / Referer / Range / `Authorization: Bearer <OAuth token>` 均无效），说明它还依赖 CLI 侧动态下发的 `x-pan-client-token`，无法脱离 CLI 自行多连接加速。
- 结论：**开放接口是「合规但慢」的通道**，限速比 Cookie 直链更狠（0.3 vs 5.2 MB/s），只适合元数据类操作，不适合承载字节流。

## 七、YunX（CYQawa，AGPL-3.0）

**定位**：Android 端网盘/直链下载器（Kotlin + Compose + OkHttp），支持 Range 分片并发、断点续传，亦可选捆绑 Gopeed 引擎。仅作下载内核设计参考，不复用代码。

### 已借鉴（2026-10-31，已落地 `app/download/engine.py`）

| # | YunX 做法 | 我们的实现 | 解决的问题 |
| --- | --- | --- | --- |
| 1 | `HttpRangePolicy.matches` 要求 206 的 `Content-Range` 起点与请求严格相等 | `_parse_content_range` + 分段内校验，不匹配即重试 | 旧实现只判状态码，CDN 返回错区间会静默写错位、文件损坏仍报成功 |
| 2 | `text/html` 响应视为防盗链/登录过期，直接失败 | `_is_html` 同时用于探测与分段 | 旧实现可能把错误页的 Content-Length 当文件大小，或把 HTML 落盘成成品 |
| 3 | 第 i 片首次请求前延迟 `min(i,8)×25ms` 错峰建连 | `STAGGER_SECONDS/STAGGER_CAP` + `start_delay`（可被 stop 事件打断） | 同时拉起 16 条连接瞬间打满握手，更容易触发风控 |
| 4 | Watchdog 每 5s 采样在飞连接，`<12KB/s` 且存活 ≥15s 则抢占换连接；冷却 10s、每片最多 3 次、每轮最多 2 路，收尾（在飞 ≤3）门槛降到 3s | `_SegmentState` + `preempt_slow`：清信号后保留已写字节重连，退避期间不占配额 | 卡慢连接会一直占着分段，过去只能等读超时（30s）后整片重试 |
| 5 | 全进程在飞分片上限（按堆预算推导 8–512） | `_inflight_slots`（32 条，按窗口申请/释放，退避时归还） | 并发 × 分段最坏 64 条连接，统一收口降低风控面与线程膨胀 |

顺带把「服务器返回比请求更短的合法区间」从**重试**改为**正常续下**（按 `Content-Range` 终点判定是否读满），避免 10 MB `range_size` 类服务端被误判为连接中断。

边界说明：完全停滞（一个字节都不来）的连接无法从读循环里检查抢占信号，仍由 HTTP 读超时兜底；httpx 的响应对象不支持跨线程关闭，强行 `close()` 有崩溃风险，因此不做主动掐断。限速期不采样、不抢占，避免把限速误判为卡死。

### 不借鉴

- **任务池 + 弹性区、线程×8 分片、512 并发、多源轮换**：为突破单连接限速设计；我们实测 32 连接反而回落到 2.8 MB/s，账号级封顶 5.2–5.6 MB/s，加并发无收益（见第六节）。
- **边写边删合并、分片级 SHA-256**：我们直接写最终 `.part` 后 `os.replace`，没有合并阶段，天然更省空间。
- **`plan.txt` 计划签名**：等价能力已在 `.part.json`（total + plan + done）与 `_load_meta` 连续性校验中实现。
- **失败区间并行重试**：当前整任务重试 + `.part` 续传，成本可接受。
- **Gopeed 引擎、SAF/通知栏/WakeLock、请求头随任务持久化**：Android 平台特性，超出本项目范围。
