# 回归测试手册

本文覆盖 P0 功能（暂停/恢复/取消、连接数与并发设置、同名策略）的自动化与手工回归步骤。
后续改动下载队列、配置中心或前端任务面板后，按本手册执行即可。

## 2. 自动化回归（推荐先跑）

脚本：[tools/e2e_p0.py](../tools/e2e_p0.py)

```powershell
.venv\Scripts\python.exe tools\e2e_p0.py
```

脚本行为：

- 自动选取云盘根目录中最大的文件（优先 ≥10 MB），下载到 `downloads/_e2e_state`；
- 临时把设置改为 `segments=2, concurrency=1, speed_limit_mbps=0.3, on_conflict=skip`；
- 结束后删除测试任务、清理测试目录、恢复原始设置；
- 全部通过时退出码为 0，否则为 1。

覆盖的 14 项断言：

| # | 断言 | 预期 |
| --- | --- | --- |
| 1 | 任务进入 `downloading` 且有进度 | `downloaded > 0` |
| 2 | 暂停后状态 | `paused` |
| 3 | 暂停后 2 秒内进度 | 不再增长 |
| 4 | `.part` 断点文件 | 保留 |
| 5 | 正式目标文件 | 未提前出现 |
| 6 | 恢复后 | 从暂停时的字节数继续增长 |
| 7 | 取消后状态 | `canceled` |
| 8 | 取消后正式目标文件 | 未生成 |
| 9 | 状态校验前 | 任务仍为 `canceled` |
| 10 | `POST /api/tasks/{id}/pause`（已取消） | `400 当前状态不可暂停` |
| 11 | `POST /api/tasks/{id}/cancel`（已取消） | `400 当前状态无需取消` |
| 12 | `POST /api/tasks/{id}/resume`（已取消） | `400 任务未暂停` |
| 13 | 取消后 `retry` | 从断点续传，进度继续增长 |
| 14 | 重试后再次取消 | `canceled` |

> 注意顺序：状态校验必须在 `retry` 之前执行。任务一旦重试回到 `downloading`，`pause` 会返回 200 并真的暂停任务，400 校验就失效了。

预期输出结尾：

```
结果：14/14 项通过
```

## 3. 手工用例：同名策略

准备（全部通过 `PUT /api/settings` 修改，保存后即时生效）：

```powershell
$b='http://127.0.0.1:8099'
Invoke-RestMethod -Method Put "$b/api/settings" -ContentType 'application/json; charset=utf-8' `
  -Body (@{segments=4; concurrency=2; speed_limit_mbps=0; on_conflict='skip'} | ConvertTo-Json) | Out-Null
```

选一个小文件（< 2 MB），连续创建同一目标路径的 4 次任务：

```powershell
$f=(Invoke-RestMethod "$b/api/files?path=/").entries |
    Where-Object { -not $_.dir -and $_.size -gt 0 -and $_.size -lt 2MB } | Select-Object -First 1
$body=@{items=@(@{fid=$f.fid; name=$f.name; dir=$false; size=$f.size; path='/_e2e_conflict'}); keep_structure=$true} | ConvertTo-Json -Depth 5
$id=(Invoke-RestMethod -Method Post "$b/api/tasks" -ContentType 'application/json; charset=utf-8' -Body $body).ids[0]
```

| 步骤 | 设置 | 预期任务状态 | 预期目录结果 |
| --- | --- | --- | --- |
| 1 | `on_conflict=skip`，首次下载 | `done` | 1 个文件 |
| 2 | `on_conflict=skip`，再次下载 | `skipped` | 仍 1 个文件，不重新下载 |
| 3 | `on_conflict=keep_both` | `done` | 2 个文件，新增 `名称 (1).扩展名` |
| 4 | `on_conflict=overwrite`（先间隔 2 秒） | `done` | 仍 2 个文件，原文件修改时间变化 |

## 4. 手工用例：排队与暂停组合

前置：`concurrency=1, speed_limit_mbps=0.5`，先创建一个大文件任务，再创建一个文件任务。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 排队中暂停 | 对第二个任务 `pause` | `paused`，`downloaded=0` |
| 排队中恢复 | `resume` | 回到 `pending`，等待并发槽位 |
| 排队中取消 | `cancel` | `canceled` |
| 暂停中取消 | 对已 `paused` 任务 `cancel` | `canceled` |
| 取消后重试 | 对 `canceled` 任务 `retry` | 从 `.part` 断点续传，进度大于取消时的值 |

## 7. 边界回归点

| 用例 | 说明 |
| --- | --- |
| 下载到不存在的子目录 | 目标目录由任务创建（`keep_structure` 子路径）。曾因 `disk_usage` 对不存在目录抛异常被吞成 0，误报「磁盘空间不足」，已在 `queue._free_space` 修复 |
| 低水位拒绝 | `low_watermark_gb` 大于剩余空间时，新任务应 `failed` 并提示空间不足 |
| 下载时段 | `schedule_enabled=true` 且当前不在时段内，任务停在 `pending`，进入时段后自动开始 |
| Cookie 失效 | 下载中 Cookie 失效，任务转 `paused`，前端出现重新登录提示 |
| 取消后的临时文件 | `.part` 与 `.part.json` 保留，用于 `retry` 续传；正式文件不会出现 |

## 9. 批量操作与任务筛选

批量接口：`POST /api/tasks/batch`，body `{"action":"pause|resume|cancel|retry|delete","ids":[...]}`；不传 `ids` 时按动作对应的状态全量处理，单次最多 500 个 id。

| 动作 | 默认作用状态 |
| --- | --- |
| `pause` | `pending/resolving/downloading/verifying` |
| `resume` | `paused` |
| `cancel` | `pending/paused/resolving/downloading/verifying` |
| `retry` | `failed/canceled` |
| `delete` | `done/failed/canceled/skipped`（进行中不受影响） |

用例：

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 全部暂停 | 两个任务（一个下载中、一个排队）执行 `pause` | 返回 `ok=2`，下载中任务 1–2 秒内变 `paused` |
| 全部恢复 | 对上述任务执行 `resume` | 回到 `pending`，按并发槽位继续 |
| 重试失败 | 制造一个 `failed` 任务后执行 `retry` | 变 `pending` 并重新下载 |
| 全部取消 | 执行 `cancel` | 活跃/暂停任务全部 `canceled` |
| 清理已结束 | 执行 `delete` | 只删除已结束任务，进行中任务保留 |
| 分组操作 | 同一文件夹批量下载后点分组头「暂停/恢复/重试/清理」 | 只影响该分组，其他分组不变 |
| 非法动作 | `{"action":"nope"}` | `400 不支持的操作` |

任务面板筛选（纯前端，不影响后端队列）：

| 操作 | 预期 |
| --- | --- |
| 搜索框输入文件名/路径片段 | 只显示匹配任务，分组按剩余子任务重新汇总 |
| 状态下拉选择「失败」「已完成」等 | 只显示对应状态；分组折叠状态保留 |
| 刷新页面 | 搜索词与状态筛选从 `sessionStorage` 恢复 |
| 无匹配结果 | 显示「没有匹配的任务」 |

## 11. 失败自动重试

设置项 `auto_retry_count`（0–10，0 关闭）与 `auto_retry_backoff`（5–600 秒）。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 越界校验 | `PUT /api/settings {"auto_retry_count":11}` | `400` |
| 自动重试 | 设置 `auto_retry_count=1, auto_retry_backoff=5`，触发一个可重试失败（如接口 404） | 任务回到 `pending`，`error` 含「自动重试 1/1」，`retry_count=1`，5 秒后重新下载 |
| 重试耗尽 | 再次失败 | 最终 `failed`，`retry_count` 不再增长 |
| 手动重试清零 | 对 `failed` 任务点重试 | `retry_count` 归零并重新排队 |
| 磁盘不足 | 剩余空间低于水位 | 直接 `failed`，不进入自动重试 |
| 界面提示 | 任务卡片 | `retry_count>0` 时显示「重试 N 次」 |

## 12. Webhook 通知

设置项 `webhook_url`（留空关闭，仅接受 `http://` / `https://`）与 `webhook_secret`（可选，最长 128 字符）。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 非法地址 | `PUT /api/settings {"webhook_url":"ftp://x"}` | `400 webhook_url 必须以 http:// 或 https:// 开头` |
| 密钥超长 | `PUT /api/settings {"webhook_secret":"<129 字符>"}` | `400 webhook_secret 不能超过 128 个字符` |
| 密钥回显 | `GET /api/settings` | `values.webhook_secret` 与保存值一致 |
| 任务开始 | 配置接收端后创建任务 | 收到 `{"event":"started","sent_at":...,"task":{"status":"downloading",...}}` |
| 任务暂停 | 下载中暂停任务 | 收到 `{"event":"paused",...}` |
| 任务完成 | 完成一个任务 | 收到 `{"event":"done","sent_at":...,"task":{...}}` |
| 最终失败 | 任务自动重试耗尽或不可重试失败 | 收到 `{"event":"failed",...,"task":{...,"error":"失败原因"}}` |
| 签名头 | 配置 `webhook_secret` 后触发任意事件 | 请求头 `X-QuarkNas-Signature: sha256=HMAC-SHA256(原始请求体)`，可用同密钥复算比对 |
| 失败重试 | 接收端首次返回 500，之后返回 200 | 同一事件共投递 2 次（最多 3 次，间隔 1s、2s） |
| 接收端不可达 | URL 指向未监听端口 | 仅日志告警「Webhook 推送失败」，不影响任务状态 |
| 代理环境 | 系统配置了 HTTP 代理 | 推送客户端使用 `trust_env=False`，本机/内网地址不被代理转发 |

验证脚本要点：本机起一个会记录请求头与请求体的接收端，第一次响应 500 制造重试；断言事件序列包含 `started`、`paused`，每条签名校验通过，且首事件投递次数 ≥2。测试后恢复 `webhook_url=""`、`webhook_secret=""`。

## 15. 队列优先级与置顶

设置项 `queue_order`（`time` 按创建顺序 / `size_desc` 大文件优先 / `size_asc` 小文件优先），任务表新增 `priority` 字段。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 顺序回显 | `GET /api/settings` | `values.queue_order` 默认为 `time` |
| 非法值 | `PUT /api/settings {"queue_order":"random"}` | `400 queue_order 只能是 time / size_desc / size_asc` |
| 手动置顶 | `concurrency=1`，A 下载中，B、C 排队，`POST /api/tasks/{C}/top` | 返回 `{"ok":true,"priority":N}`；A 结束/取消后 C 先开始，C 完成后才轮到 B |
| 非排队任务置顶 | 对 `downloading` / `done` 任务调用置顶 | `400`，提示「只有排队中的任务可以置顶」 |
| 任务不存在 | 对不存在的 id 置顶 | `400 任务不存在` |
| 大文件优先 | 切换 `queue_order=size_desc` 后刷新，重复上例（先入队小文件再入队大文件） | 后入队的大文件先开始 |
| 小文件优先 | 切换 `queue_order=size_asc` | 小文件先开始 |
| 切换顺序即时生效 | 下载中修改 `queue_order`，已有若干 `pending` 任务 | 存量排队任务按新顺序重排（无需重启） |
| 置顶优先级不受顺序影响 | `queue_order=size_desc` 下置顶一个小文件 | 小文件仍排在所有排队任务之前 |
| 界面 | `pending` 任务卡片 | 显示「置顶」按钮，点击后提示「已置顶，将在当前任务结束后优先下载」 |

验证脚本要点：`concurrency=1`、`speed=0.2`（MB/s）拉长下载窗口；用 mp4 占住唯一 worker，再用 png/pdf 排队；置顶 pdf 后取消 mp4，记录 `started` 事件顺序断言 pdf 先于 png。测试后恢复 `concurrency=2`、`speed=0`、`queue_order=time`，并清理 `.part` / `.part.json`。

## 16. 自动清理任务记录

设置项 `cleanup_days`（0–365，0 为关闭，默认 0）。队列内每小时检查一次，启动时也会立即执行一次。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 越界校验 | `PUT /api/settings {"cleanup_days":366}` | `400 cleanup_days 取值范围 0–365` |
| 非法类型 | `PUT /api/settings {"cleanup_days":"abc"}` | `400 cleanup_days 必须是整数` |
| 关闭状态 | `cleanup_days=0` | 不删除任何记录 |
| 清理过期记录 | 设 `cleanup_days=1`，把某条已完成任务的 `updated_at` 改到 1 天前，重启服务 | 该记录被删除，接口返回的任务列表中不再出现；日志「自动清理 N 条任务记录（保留 1 天）」 |
| 保留期内的记录 | 同上，但任务 `updated_at` 在 1 天内 | 记录保留 |
| 不删除文件 | 清理前后对比 `downloads` 目录 | 落盘文件全部保留（只删记录） |
| 进行中任务 | 任务处于 `downloading` / `pending` / `paused` | 不受影响 |
| 界面即时移除 | 打开页面时触发清理 | 收到 SSE `removed` 事件，卡片自动消失 |

验证脚本要点：停止服务后直接用 sqlite3 写入一条 `updated_at` 为 5 天前的 `done` 记录，同时写入 `setting.cleanup_days=1`；启动服务后 `GET /api/tasks` 断言该记录已消失、其他记录与下载文件仍在；最后把 `cleanup_days` 恢复为 0。

## 17. 低速自动扩容

慢源站常见「单连接被限死、总速度随连接数线性增长」。引擎每 5 秒采样一次，当总速度低于 3 MB/s 且单连接低于 0.35 MB/s 时，把剩余量最大的分段一分为二、新增一个连接，最多到 16 段；每加一次连接后对比单连接速度，跌破上次的 70% 视为已到通道上限并停止；设置了总限速时不触发。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 慢源站自动扩容 | 下载被限速的文件（单连接约 0.1 MB/s） | 日志连续出现「低速扩容：连接数增至 N」，任务详情分段数从 4/8 逐级涨到 16 |
| 快源站不扩容 | 下载正常速度的文件（>3 MB/s） | 分段数保持设置值不变，日志无扩容记录 |
| 到上限停止 | 扩容到 16 段 | 不再新增；单连接速度跌破阈值时提前停止 |
| 限速优先 | 设置总限速 > 0 | 不做扩容（低速度是自身限速导致） |
| 断点续传兼容 | 扩容后暂停，再恢复或重启服务 | `.part.json` 里扩容后的分段方案被原样接管，不从头重下 |
| 数据完整性 | 扩容后下载完成 | 文件大小与 MD5/内容与源一致，`.part`/`.part.json` 被清理 |
| 大文件实测 | 12.8 GB mkv（`dl-pc-zb` 节点） | 窗口化后 8 段稳定 10–12 MB/s（改造前 16 段仍只有 0.79 MB/s） |

离线验证脚本要点：用 `ThreadingHTTPServer` 提供支持 Range 的本地文件，在 handler 里按 64KB 睡固定时长模拟单连接限速；把 `engine.ADAPTIVE_SAMPLE` 调成 1 秒加速测试。断言「快源站分段数不变」「慢源站分段数 ≥ 10」「下载内容哈希一致」「`_load_meta` 能接管扩容后的方案、拒绝大小不符或分段不连续的断点文件」。注意脚本需设置 `NO_PROXY=127.0.0.1` 或 `trust_env=False`，否则会被系统代理拦成 502。

### 17.1 Range 窗口化续传

夸克 CDN 对「单次 Range 请求跨度」敏感，与连接新旧无关。同一 URL、同一偏移实测：8 MB 2.03/1.98、16 MB 2.24/2.17、32 MB 2.22/2.12、64 MB 1.95/2.07、128 MB 1.97/2.05、256 MB 1.8/1.84、**512 MB 0.09/0.09、1 GB 0.09/0.09 MB/s**。原实现按分段余量请求（数百 MB～GB），所以每条连接只有 56–90 KB/s。现在每条连接固定只取 `RANGE_WINDOW`（64 MB）内的窗口，写完立刻重开连接续下一窗口。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 窗口切分 | 用支持 Range 的本地服务下载 >3 个窗口的文件，把 `engine.RANGE_WINDOW` 调成 1 MB | 服务端收到的 `Range` 起点依次为 0、1 MB、2 MB…；文件内容哈希一致 |
| 大文件提速 | 下载 12.8 GB / 15.2 GB mkv | 单任务稳定 10 MB/s 以上，不再随分段变长而衰减到 1 MB/s |
| 窗口边界 | 分段终点不落在 64 MB 整数倍上 | 最后一个窗口在 `limits[idx]` 处截断，总字节数精确等于文件大小 |
| 扩容不越界 | 下载中途触发扩容缩短分段 | 当前窗口以缩短后的终点截断，不越界写；断点方案仍可接管 |
| 慢节点保护 | 连接开局 5 秒内低于 0.3 MB/s | 判定为慢节点，不再反复重连，交给自动扩容加连接 |
| 限速不误判 | 设置总限速 > 0 | 限速期间不触发「连接低速轮换」，日志无高频重连 |
| 账号级降速 | 连续大流量后所有连接（含新建）降到 0.1 MB/s | 属通道级限速，加连接无效；暂停 3–5 分钟后恢复约 2 MB/s |

## 18. 风控自适应（连续 403 自动降并发并冷却）

180 秒窗口内累计 2 次 `403` 即进入冷却；冷却从 120 秒起、每次翻倍、上限 600 秒。冷却期内并发减半（最少 1）、分段压到 ≤2、关闭低速自动扩容，多余 worker 在取任务前等待；任意任务下载成功即清零并恢复原并发；连续 6 次冷却后仍 403 则任务判 `failed`。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 首次 403 | 单次 403 | 不冷却，任务回到 `pending` 重试 |
| 触发冷却 | 180 秒内第 2 次 403 | 日志「进入风控冷却 120 秒，并发降至 N，分段降至 2」 |
| 冷却状态接口 | `GET /api/tasks` | `risk.active=true`、`seconds>0`、`concurrency` 为减半值、`segments<=2` |
| SSE 推送 | 保持页面打开 | 收到 `risk` 事件，任务面板顶部出现「风控冷却」条与秒级倒计时 |
| 冷却期不扩容 | 冷却期内下载慢文件 | 分段数保持 ≤2，无「低速扩容」日志 |
| 冷却结束 | 倒计时归零 | 日志「风控冷却结束，恢复并发 N」，前端提示条自动消失并刷新任务 |
| 连续触发翻倍 | 冷却结束后再次触发 | 冷却 240 秒 → 480 秒 → 600 秒封顶（`strikes` 递增） |
| 成功清零 | 冷却期内有任务下载完成 | 计数清零，并发恢复，`strikes=0` |
| 反复失败 | 第 6 次冷却后仍 403 | 任务 `failed`，`error` 含风控提示，不再无限重试 |
| 设置变更 | 冷却中修改 `concurrency` | 冷却结束后按新设置恢复，不残留旧并发 |

离线验证要点：构造临时 `DB` + `TaskRunner`，连续调用 `_note_risk()` —— 第 1 次返回 `0`、第 2 次返回 `120`、抓一次窗口后再两次返回 `240`；断言 `risk_state()` 在冷却期 `concurrency/segments` 为减半值，`_clear_risk()` 后恢复（本轮已通过）。

## 19. 拖拽排序

`pending` 任务卡片左侧有拖拽手柄（6 点图标），拖动到另一张 `pending` 卡片的上/下半区即插入到其前/后。前端先按 `priority` 乐观重排，再调用 `POST /api/tasks/reorder`。

接口约定：body `{"ids":[3,1,2]}`，数组顺序即目标顺序；只处理 `pending` 任务，其余状态忽略；单个 id 的 `priority = total - index`（越靠前越大）；`pending` 任务按 `priority` 降序、再按 `id` 升序出队。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 拖拽重排 | 三个排队任务 A/B/C，把 C 拖到 A 之前 | 卡片顺序立即变为 C/A/B，接口返回 `{"ok":true,"count":3}` |
| 精度校验 | SQL 查询 `priority` | C=3、A=2、B=1 |
| 实际出队顺序 | `concurrency=1`，取消正在下载的任务 | 依次开始 C → A → B |
| 刷新保持 | 重排后刷新页面 | 顺序不变（`priority` 已落库） |
| 空列表 | `{"ids":[]}` | `400 排序列表为空` |
| 无排队任务 | 只传 `done/downloading` 的 id | `400 没有可排序的排队任务` |
| 超量 | 超过 1000 个 id | `400 一次最多排序 1000 个任务` |
| 重复 id | `{"ids":[2,2,1]}` | 去重后按 `[2,1]` 处理 |
| 失败回滚 | 断网或被鉴权拦截 | 提示错误并重新拉取任务列表，恢复真实顺序 |
| 与置顶一致 | 拖到最上后再点「置顶」 | 两种方式都写 `priority`，结果一致 |

## 21. 下载协议校验（借鉴 YunX）

引擎在 `app/download/engine.py` 中新增三项防御，改动只影响异常路径：

| 用例 | 构造方式 | 预期 |
| --- | --- | --- |
| 正常 206 | 本地 Range 服务（4 段、5 MB） | 下载完成，MD5 与源一致 |
| 短区间 | 服务端每次只返回 1 MB（小于请求跨度） | 按 `Content-Range` 终点续下，不触发重试，MD5 一致 |
| 区间错位 | 206 的 `Content-Range` 起点比请求大 1 | 分段内重试；重试耗尽后 `failed`，错误含「Content-Range 起点」 |
| HTML 错误页 | 探测或分段请求返回 `Content-Type: text/html` | 任务直接 `failed`，错误含「HTML 页面」，不生成目标文件 |
| 错峰建连 | 分段数 ≥ 4，抓包或看日志时间 | 第 i 段首次请求依次延迟 25ms（上限 200ms） |
| 真实直链冒烟 | 云盘小文件（< 2 MB）建任务 | `done`，`downloaded == size`，落盘大小一致 |

已用本地 `ThreadingHTTPServer` 跑通前四项（4/4），并用真实直链下载 666 KB PDF 冒烟通过。

## 22. 慢连接抢占与全局在飞上限（借鉴 YunX）

引擎新增两个约束：看门狗每 5 秒采样一次在飞连接，极慢的连接主动断开并换连接续传（已写字节保留）；全进程同时最多 `MAX_INFLIGHT_CONNECTIONS`（32）条连接，按窗口申请、退避期间归还。

| 用例 | 构造方式 | 预期 |
| --- | --- | --- |
| 抢占触发 | 本地 Range 服务把某区间限速到 32 KB/s，`PREEMPT_TICK/AGE/BPS` 临时调小 | 日志出现「卡慢连接：分段 N …换连接续传」，任务完成且 MD5 一致 |
| 次数上限 | 同一分段持续极慢 | 该分段累计抢占不超过 `PREEMPT_MAX_PER_SEGMENT`（3）次，不无限抖动 |
| 冷却间隔 | 抢占后立刻再采样 | 同一分段 `PREEMPT_COOLDOWN`（10s）内不重复抢占 |
| 收尾门槛 | 在飞连接 ≤ 3 | 观察窗口降为 3s，尾部不被一条卡死连接拖住 |
| 全局上限 | 同时跑两个多分段任务，上限临时改为 2 | 服务端观测到的峰值并发 ≤ 2，两个文件字节数均等于源大小 |
| 配额归还 | 上述任务全部结束 | 信号量计数回到初值（无泄漏）；成功后也不会重复 release |
| 退避归还 | 分段出现 5xx 进入退避 | 退避睡眠期间不占配额，其他分段可立即建连 |
| 限速期不抢占 | 设置总限速 > 0 | 不采样、不抢占，日志无「卡慢连接」 |
| 取消响应 | 等待全局配额时取消任务 | 0.5s 轮询内退出，不残留线程 |
| 默认参数冒烟 | 真实直链小文件建任务 | `done`，`downloaded == size`，日志无「卡慢连接」误报 |

离线验证要点：`ThreadingHTTPServer` + 48 MB payload，`/slow` 路径对前 512 KB 限速 32 KB/s；把 `engine.PREEMPT_*` 调小后断言出现 ≥1 次抢占且哈希一致；另用 `monkeypatch` 把 `engine._inflight_slots` 换成 `BoundedSemaphore(2)` 并发跑两个 2 段任务，统计服务端峰值并发并断言结束后 `_value` 复原（本轮 2/2 通过）。

边界：完全停滞（一个字节都不来）的连接无法从读循环里检查抢占信号，仍由 HTTP 读超时兜底；httpx 响应对象不支持跨线程安全关闭，因此不主动 `close()`。
